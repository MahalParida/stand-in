# Stand-In as an Alexa+ add-on (MCP Toolkit)

This folder holds the add-on listing for connecting the real Alexa+ to the Stand-In MCP server:

- `addon-package/addon.json`: the manifest template. Every URL is written as `${PUBLIC_BASE_URL}`.
- `../scripts/render-addon.mjs`: fills in `PUBLIC_BASE_URL`, checks the documented field limits, and with
  `--verify` fetches every URL.

The server provides everything else that Alexa reads:

| Path | What |
| :--- | :--- |
| `/mcp` | Streamable HTTP MCP endpoint. Accepts `STANDIN_TOKEN` or an OAuth access token. Without a valid token it answers 401 with no `WWW-Authenticate` header, which is what starts account linking. |
| `/.well-known/oauth-protected-resource` | RFC 9728 document: `resource` = `${PUBLIC_BASE_URL}/mcp`, `authorization_servers` = `[${PUBLIC_BASE_URL}]`, `scopes_supported` = `["standin"]` |
| `/.well-known/oauth-authorization-server` | RFC 8414 document: `/authorize`, `/token`, PKCE `S256`, `client_secret_basic` and `client_secret_post` |
| `/authorize`, `/token` | the built-in OAuth 2.1 server (one pre-registered client, PKCE S256, refresh-token rotation) |
| `/privacy`, `/terms` | the listing's privacy policy and terms of use |
| `/addon-assets/icon-{72,64,88,126,180,241}x….png`, `/addon-assets/carousel-600x900.png` | the listing media (original artwork, generated by `apps/mcp-server/scripts/gen-addon-assets.mjs`) |

Amazon's docs used for this setup (July 2026): MCP QuickStart, Account Linking for MCP Add-ons, Authentication,
Alexa AI CLI reference, and Test with the Web Simulator, all under
`https://developer.amazon.com/docs/alexaplus/add-ons/`. Where those docs are silent, the server follows standard
OAuth 2.1 behaviour and the choice can be changed in `.env` (see [Open questions](#open-questions)).

## You enter the OAuth client in two places

| Value | On the Stand-In server | In Alexa |
| :--- | :--- | :--- |
| Client ID | `OAUTH_CLIENT_ID` in `.env`, or in the Lightsail environment | `alexa-ai configure-account-linking --client-id <same value>` |
| Client secret (required) | `OAUTH_CLIENT_SECRET` in `.env` | the CLI's masked prompt, or the `ALEXA_CLIENT_SECRET` environment variable. Never pass it as a command-line flag. |
| Redirect URIs | `OAUTH_REDIRECT_URIS` (comma list), copied from Alexa | printed by `configure-account-linking` and listed in the Alexa+ Developer Hub |

The client ID and secret are values you make up. Generate them locally; the commands below append them to `.env`
without printing them:

```bash
printf 'OAUTH_CLIENT_ID=standin-alexa\n' >> .env
printf 'OAUTH_CLIENT_SECRET=%s\n' "$(openssl rand -base64 33 | tr -d '/+=')" >> .env
printf 'OAUTH_LINK_PASSCODE=%s\n' "$(openssl rand -hex 6)" >> .env   # you type this on the consent page
printf 'OAUTH_CLIENT_CREDENTIALS=true\nMCP_PUBLIC_DISCOVERY=true\n' >> .env
```

Remove any empty `OAUTH_*=` / `MCP_PUBLIC_DISCOVERY=` lines left over from `.env.example` and keep exactly one line
per key. To see the passcode, open `.env` in your editor; do not print it in a shared terminal.

All four are required for a server Alexa can reach:

- **`OAUTH_CLIENT_SECRET` and `OAUTH_LINK_PASSCODE`.** The server refuses to start without them when
  `PUBLIC_BASE_URL` is a public host or `HOST` is not loopback. The client ID and Alexa's redirect URIs are not
  secret, so without a passcode anyone could approve their own linking request, and without a secret anyone could
  redeem the code. The passcode must be at least 8 characters. Wrong guesses are capped at
  `OAUTH_PASSCODE_MAX_FAILURES` per hour in total (default 20) and a third of that per client address; once the cap is
  hit, approvals are refused for up to an hour (restarting the server clears it).
- **`OAUTH_CLIENT_CREDENTIALS=true` and `MCP_PUBLIC_DISCOVERY=true`.** Alexa+ fetches the tool list during
  `alexa-ai deploy`, before any user has linked. Amazon's Authentication page has it use a Tier 1
  `client_credentials` token (`mcp:service`, Basic auth with the client ID and secret) for initialize and tools/list.
  `MCP_PUBLIC_DISCOVERY` also lets an unauthenticated initialize and tools/list through, in case Alexa does not
  fetch a Tier 1 token for a public server. Either way `tools/call` without a user token still answers 401 with no
  `WWW-Authenticate`, which is what starts account linking.

## Steps

### 1. Install the Alexa AI CLI and sign in

Install the CLI as described in "Set Up Your Development Environment" in the Alexa+ add-on docs. Then:

```bash
alexa-ai configure            # Login with Amazon in the browser; credentials go to ~/.alexa-ai/credentials
# alexa-ai configure --no-browser   # on SSH or a headless machine
```

### 2. Get a public HTTPS URL

Alexa needs a public `https://` URL for the endpoint, every image and the privacy and terms pages. Choose one:

**A. Lightsail (recommended; the URL stays the same).** Follow [docs/DEPLOY.md](../docs/DEPLOY.md). The deploy
script sets `PUBLIC_BASE_URL` to the service URL and passes the `OAUTH_*` values from `.env` (section 2a there). It
refuses to deploy without `OAUTH_CLIENT_SECRET` and `OAUTH_LINK_PASSCODE`, and sets `OAUTH_CLIENT_CREDENTIALS` and
`MCP_PUBLIC_DISCOVERY` to `true` unless you set them otherwise.

**B. A tunnel to your machine (local development).** Run any HTTPS tunnel (the QuickStart mentions cloudflared)
to the server's local port (`PORT` in `.env`; 8787 if unset), then set these in `.env` and start the server with
`pnpm --filter @standin/mcp-server start`:

```bash
PUBLIC_BASE_URL=https://<your-tunnel-host>
STANDIN_ALLOWED_HOSTS=<your-tunnel-host>,127.0.0.1:<PORT>,localhost:<PORT>
TRUST_PROXY=true
OAUTH_CLIENT_CREDENTIALS=true
MCP_PUBLIC_DISCOVERY=true
```

`PUBLIC_BASE_URL` must be the exact public origin, with no trailing slash. It becomes the OAuth issuer and the
canonical resource `${PUBLIC_BASE_URL}/mcp`, and Alexa requires that resource to match the manifest endpoint
exactly. A quick tunnel gets a new host name every time it starts. When the host name changes, you must render the
manifest again, run `alexa-ai deploy` again, and link the account again, so use a named tunnel or Lightsail for
anything longer than one session.

Check the server from outside:

```bash
node scripts/render-addon.mjs --base-url "$PUBLIC_BASE_URL" --verify
```

`--verify` checks that every icon, the carousel, `/privacy` and `/terms` return 200 with the right content type,
that the PRM `resource` equals the manifest endpoint, that `authorization_servers[0]` equals the issuer, that `S256`
is advertised, that Alexa can discover the tools before linking (an unauthenticated initialize + tools/list returns
the tools, or `grant_types_supported` includes `client_credentials`), and that a `tools/call` without a token gets
401 with no `WWW-Authenticate` header. Do not run `alexa-ai deploy` until it passes.

### 3. Scaffold the add-on and render the manifest

```bash
mkdir -p alexa-addon/project && cd alexa-addon/project      # gitignored
alexa-ai new mcp --name "Stand-In" --locale en-US --mcp-server-url "$PUBLIC_BASE_URL/mcp"
# "Does your Add-on require account linking? (Y/N)"  ->  Y   (writes accountLinking.enabled: true)
cd ../..
node scripts/render-addon.mjs --base-url "$PUBLIC_BASE_URL" --out alexa-addon/project/<created-dir>/addon-package/addon.json
```

`render-addon.mjs` overwrites the store listing and the MCP endpoint. Fields that the CLI wrote and the template
does not set are kept. The template also sets `accountLinking.enabled: true`, the only account-linking manifest
field that is documented. No client ID, URLs or scopes go into `addon.json`. Alexa discovers the endpoints and
scopes from the well-known documents.

### 4. Configure account linking

Run this from the project directory, so that the CLI can find `.alexa-ai/config.json`. The secret is read from
`.env` into the environment and is never printed:

```bash
ALEXA_CLIENT_SECRET="$(grep -E '^OAUTH_CLIENT_SECRET=' ../../.env | head -n 1 | cut -d= -f2-)" \
  alexa-ai configure-account-linking --addon-id <your-addon-id> --stage development \
  --client-id "$(grep -E '^OAUTH_CLIENT_ID=' ../../.env | head -n 1 | cut -d= -f2-)"
```

Enter the secret here. Do not leave the masked prompt empty: the public server requires a confidential client, and
the Tier 1 `client_credentials` grant only works with a secret. A secret on only one side gives `invalid_client`.

The CLI prints a discovery summary. Check that it shows:

- authorization endpoint `${PUBLIC_BASE_URL}/authorize`
- token endpoint `${PUBLIC_BASE_URL}/token`
- PKCE `S256`
- scope `standin` (plus `mcp:service` for Tier 1)
- grant types including `client_credentials`

`alexa-ai new` might not create an add-on ID. If so, run `alexa-ai deploy` once to get one, then run this step.

### 5. Register Alexa's redirect URIs

The CLI and the Alexa+ Developer Hub list the redirect URIs that Alexa may use. They have the form
`https://alexa.amazon.com/api/skill/link/<vendor-id>`, and there are several, because the URI depends on where the
customer registered the device. Copy every one of them into `.env` as a comma list:

```bash
OAUTH_REDIRECT_URIS=https://alexa.amazon.com/api/skill/link/XXXX,https://<other-host>/api/skill/link/XXXX
```

Restart the server, or redeploy Lightsail. The server compares the URI exactly, character for character. If a
request uses an unregistered URI, the server shows an error page and does not redirect.

### 6. Deploy the add-on

```bash
cd alexa-addon/project/<created-dir> && alexa-ai deploy
```

Review the account-linking summary and confirm. Alexa caches the auth metadata and the tool list when you deploy.
Run `alexa-ai deploy` again whenever `PUBLIC_BASE_URL`, the scopes, the client settings or the MCP tools change.
To read the stored configuration back, run `alexa-ai get-account-linking --stage development`.

### 7. Test in the web simulator

1. Open the developer console, go to **My Add-ons**, and choose **Test in Simulator** for Stand-In. You can also
   use the **Simulator** button in the left navigation.
2. Choose **Stage: development** and **Mode: Isolation**. Isolation sends every utterance to this add-on only.
3. In **Ask Alexa**, type `Ask Stand-In to call BharatNet about my broadband outage`.
4. The first tool call gets a 401, and Alexa starts account linking. Amazon's docs describe linking through a QR
   code on screen devices or a push notification to the Alexa app. Finish it on the add-on's detail page in the
   Alexa app. The Stand-In consent page opens: "Link Stand-In to Alexa for <STANDIN_USER_NAME>". Enter the passcode
   and choose **Approve**.
5. Ask again. Alexa now sends the access token, so the call runs and `call_status` reports progress.

To use a real Echo device, open **Physical Device Config**, then **Configuration Override**. Choose the device and
the development stage, then save.

Before any end-to-end test, try the server with MCP Inspector or the Local Inspector. Use
`Authorization: Bearer $STANDIN_TOKEN`, which still works next to OAuth.

## Troubleshooting

| Symptom | Cause |
| :--- | :--- |
| `alexa-ai deploy` blocks on S256 | `/.well-known/oauth-authorization-server` is not reachable at `PUBLIC_BASE_URL`. Run `render-addon.mjs --verify`. |
| The consent page says "Redirect URI not registered" | Add every URI from step 5 to `OAUTH_REDIRECT_URIS`, then restart or redeploy. |
| Redirect back with `error=invalid_target` | The `resource` Alexa sent is not `${PUBLIC_BASE_URL}/mcp`. Check for a trailing slash or a stale tunnel host, then render and deploy again. |
| Redirect back with `error=invalid_scope` | Alexa asked for a scope that is not in `OAUTH_SCOPES`. Add it (space or comma list), restart, and run `alexa-ai deploy`. |
| `invalid_client` at `/token` | The client secret differs between `.env` and `configure-account-linking`, or only one side has a secret. |
| Users must link again after a server change | A Lightsail redeploy resets the SQLite volume. With a tunnel, a new host name changes the resource. |
| Alexa lists no tools, or `alexa-ai deploy` fails tool discovery | `OAUTH_CLIENT_CREDENTIALS` or `MCP_PUBLIC_DISCOVERY` is not `true`, or `OAUTH_CLIENT_SECRET` is missing. Fix `.env`, restart or redeploy, run `render-addon.mjs --verify`, then `alexa-ai deploy` again. |
| The server will not start: `invalid server configuration: OAUTH_LINK_PASSCODE` / `OAUTH_CLIENT_SECRET` | A public deployment needs both (passcode at least 8 characters). |
| The consent page says "Linking temporarily locked" | Too many wrong passcodes this hour. Wait for the hour to pass, or restart the server. |

## Open questions

These points are not settled by Amazon's docs. Each one is configurable.

- **Client authentication at `/token`.** The docs' sample token request has no secret. The server accepts
  `client_secret_basic` and `client_secret_post`. A PKCE-only public client is allowed only on a loopback-only dev
  server, because on a public server it would let anyone redeem a self-approved code.
- **The `--config-file` form of `configure-account-linking`.** The CLI reference documents it, but no schema for the
  file is published, so these steps use `--client-id` with the masked prompt.
- **The Tier 1 `client_credentials` grant.** Amazon describes it for a *private* MCP server, but also says Tier 1
  "must be established before user-level account linking occurs" and that initialize/tools/list use it. These steps
  turn it on (`OAUTH_CLIENT_CREDENTIALS=true`) together with `MCP_PUBLIC_DISCOVERY=true`, so discovery works either
  way. The grant issues only `mcp:service`, with `expires_in` of at most 3600 and no refresh token. Those tokens can
  only initialize and list.
- **Scopes.** The docs' example uses `openid`, but OIDC is listed as unsupported. Stand-In advertises only `standin`.
  If Alexa asks for more, add the scopes to `OAUTH_SCOPES`.
- **Redirect hosts.** No fixed list is published. Always copy the list from the CLI output or the Developer Hub.
